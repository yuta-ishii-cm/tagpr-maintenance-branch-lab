# 残った課題

この形で解決していないことと、案件ごとに決める必要があることです。

## 中身のコンフリクトは人が解消する

自動で解消するのは、versionFile と CHANGELOG.md だけのコンフリクトです。ほかのファイルがコンフリクトしたら、同期 PR の本文や修正候補のコメントにファイル名が書かれるので、人が解消します。

## 修正候補を付け替えるタイミング

検証リポジトリでは、機能リリースのタグを作った時点で、開いている修正候補を新しい保守ブランチに付け替えています。

タグを作ってから本番にデプロイするまでの間は、本番でまだ1つ前の系統が動いています。この間に本番向けの hotfix を出すなら、向き先を1つ前の保守ブランチに戻す必要があります。付け替えを本番へのデプロイ時にする、自動では付け替えない、といった選び方もあります。

## 保守ブランチの保護

`release/**` を ruleset で保護すると、HOTFIX_RELEASE の直接の push（versionFile・CHANGELOG.md の更新）と、TAGPR による保守ブランチの作成が止まります。保護するなら、自動化で使うトークン（GitHub App など）をバイパスの対象に加えます。削除も禁止するなら、古い保守ブランチを消す人もバイパスに加える必要があります。

## 古い保守ブランチを消すタイミング

1つ前の系統の保守ブランチは、次の系統を本番に出したら消す想定です。

- 早すぎると、本番がまだ古い系統なのに、そこへ hotfix を出せなくなる（タグからブランチを作り直せば戻せる）
- 消す前に、そのブランチに向けた修正候補や同期 PR が残っていないかを確かめる

## submodule

submodule の参照先を保守ブランチと main の両方で変えていると、同期 PR がコンフリクトします。自動解消の対象外なので、どちらを残すかを人が決めます。

## 検討したほかの方法: release-please

リリースのツールを [release-please](https://github.com/googleapis/release-please) に替える案も、別の検証リポジトリ（[release-please-maintenance-branch-lab](https://github.com/yuta-ishii-cm/release-please-maintenance-branch-lab)）で試しました。

- リリース PR のブランチ名に対象のブランチ名が入るので、保守ブランチごとにリリース PR を作れる（tagpr のようにぶつからない）
- 一方で、同期 PR の作成やコンフリクトの解消は、自前で作る必要が残った。手順の数は、tagpr の形とほぼ同じだった
- Conventional Commits でないコミットは無視される（リリースされない）。マージコミットだと CHANGELOG の項目が重複するので、squash マージにする必要がある

コミットの書き方とマージの方法を変えるほどの利点は無いと判断し、tagpr のままにしました。
